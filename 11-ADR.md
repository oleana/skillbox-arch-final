# ADR-012. Использование Integration Service

## Статус

Согласовано

## Контекст

Платформа должна интегрироваться со спортивными устройствами, фитнес-функциями телефона, существующими приложениями компании и интернет-магазином.

Если каждый сервис будет интегрироваться с внешними системами самостоятельно, архитектура станет сильно связанной и сложной в сопровождении.

## Решение

Использовать Integration Service как отдельный слой интеграции с внешними системами.

Integration Service отвечает за:

- подключение спортивных устройств;
- получение данных из Apple Health / Google Health Connect;
- интеграцию с существующими спортивными приложениями компании;
- нормализацию внешних данных;
- публикацию событий устройств в Kafka.

## Альтернативы

| Альтернатива | Причина отказа |
|-------------|----------------|
| Прямые интеграции из каждого сервиса | Дублирование логики и высокая связанность |
| Интеграция только через API Gateway | Gateway не должен содержать бизнес-логику интеграций |
| Отдельный сервис на каждого поставщика устройств | Усложняет архитектуру на старте |

## Последствия

Плюсы:

- единая точка работы с внешними системами;
- проще добавлять новые устройства;
- доменные сервисы не зависят напрямую от внешних API.

Минусы:

- Integration Service становится важным компонентом;
- требуется обработка ошибок внешних API;
- нужна нормализация данных от разных поставщиков.

# ADR-013. Использование React Native для мобильных приложений

## Статус

Согласовано

## Контекст

Платформа должна предоставлять мобильное приложение для iOS и Android с одинаковым набором функций: тренировки, социальные функции, соревнования, интеграция с устройствами и push-уведомления.

Компания заинтересована в быстром выводе новых функций одновременно на обеих платформах и в снижении затрат на разработку и сопровождение мобильных клиентов силами ограниченного числа мобильных разработчиков.

## Решение

Использовать React Native для разработки мобильного приложения в виде единой кодовой базы для iOS и Android.

Основные аспекты применения:

- общая бизнес-логика и UI-компоненты для обеих платформ;
- нативные модули (Native Modules / Turbo Modules) для интеграции с Apple Health, Google Health Connect и спортивными устройствами через Bluetooth;
- единый CI/CD pipeline для сборки и публикации приложения в App Store и Google Play;
- переиспользование команды фронтенд-разработчиков (JavaScript/TypeScript) для мобильной разработки.

## Альтернативы

| Альтернатива | Причина отказа |
|-------------|----------------|
| Отдельные нативные приложения (Swift/Kotlin) | Максимальная производительность и доступ к платформенным API, но двойные затраты на разработку, тестирование и поддержку, более медленный Time-to-Market |
| Flutter | Хорошая производительность и единая кодовая база, но требует отдельного стека (Dart) и снижает переиспользование существующей фронтенд-экспертизы команды |
| PWA / Web-приложение | Не обеспечивает полноценного доступа к нативным API устройства (Bluetooth, фоновые задачи, push-уведомления, интеграции со здоровьем) |

## Последствия

Плюсы:

- единая кодовая база и команда разработки для iOS и Android;
- сокращение затрат и времени на разработку и поддержку функционала;
- переиспользование JavaScript/TypeScript экспертизы;
- широкая экосистема готовых библиотек и нативных модулей;
- более быстрый релиз новых функций одновременно на обеих платформах.

Минусы:

- ниже производительность по сравнению с полностью нативными приложениями для отдельных ресурсоёмких сценариев (например, обработка потоков геолокации в реальном времени);
- зависимость от совместимости сторонних библиотек с новыми версиями React Native и ОС;
- часть функций (сложные фоновые вычисления, специфичные аппаратные интеграции) может требовать написания нативного кода отдельно для iOS и Android.
